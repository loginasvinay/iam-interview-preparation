01 — Federation

Who vouches?

The IdP asserts identity. SAML for legacy enterprise XML assertions, OIDC for modern JSON / mobile. Trust = metadata, signing keys, issuer.

02 — Authentication

Who proves?

The user proves possession / knowledge / inherence. Today: passkeys / WebAuthn first, then OTP, push, magic link as fallbacks by assurance level.

03 — Authorization

Who permits?

OAuth 2.0 delegates access. Scopes + claims + policies decide what a token can do — authentication alone never grants access.

OAuth 2.0 → 2.1 — delegated authorization, not login

Use when: an app needs limited access to an API on someone’s behalf. OAuth alone does not tell you who logged in — that’s OIDC’s job.

✕ Implicit flow — removed in 2.1✕ ROPC / password grant — removed✓ Auth Code + PKCE for all clients✓ Exact redirect URI match

Grants that remain: Authorization Code (+PKCE), Client Credentials (machine-to-machine), Device Code (TV / CLI), Refresh Token (with rotation). 2.1 consolidates best practice — it’s not a new wire protocol.

SAML 2.0 — enterprise federation workhorse

Use when: enterprise SSO, legacy SaaS, government. XML assertion, signed (and sometimes encrypted), carried via browser POST / Redirect binding.

IdP-initiated & SP-initiatedNameID + AttributeStatementMetadata exchange = trust

Interview line: “SAML and OIDC solve the same federation problem — SAML is XML, POST-bound, enterprise-proven; OIDC is JSON, REST-friendly, and wins on mobile / native.” Watch: assertion replay, clock skew, signature wrapping, unsolicited (IdP-init) responses.

WebAuthn / FIDO2 — the authentication ceremony

Not a federation protocol. It’s how the authenticator proves you: public-key credential, origin-bound, phishing-resistant. Pairs with any IdP — Okta, Entra, 1Kosmos — as a factor or primary login.

Auth Code + PKCE flow

Step through it

Why PKCE? It binds the code to the device that started the flow — so an intercepted code is useless. Originally for public clients (mobile/SPA), now required for all clients in OAuth 2.1, including confidential ones as defence-in-depth.

Passkeys & WebAuthn

The 2026 centrepiece

Synced passkeys

Private key syncs via iCloud Keychain / Google Password Manager. Best UX, cross-device recovery built in.

Consumer / CIAMAAL2 capable*

*Per NIST 800-63B / -63-4 guidance, depends on sync fabric controls. Enterprises that need strict device binding may not accept them for high assurance.

Device-bound passkeys

Key never leaves one authenticator — security key (YubiKey) or platform TPM. Strongest binding, harder recovery.

Workforce / high assuranceAttestation matters here

Use attestation to verify authenticator model in regulated / workforce enrolment — rarely in consumer, where it adds friction and privacy concerns.

Two ceremonies — don’t mix them up

Registration: server challenge → authenticator creates key pair → public key + credential ID stored server-side.   Authentication: new challenge → authenticator signs it → server verifies with stored public key, checks sign-count for cloning.

Interview trap: “Are passkeys biometrics?” No. Biometrics (Face ID / fingerprint) only unlock the private key locally — biometric data never leaves the device and is never sent to the server.

Lifecycle, SCIM & linking

SCIM 2.0

Provisioning protocol — creates / updates / deprovisions users & groups via REST (/Users, /Groups). The “JML” engine: Joiner creates, Mover updates entitlements, Leaver deactivates — same day, not next ticket.

SCIM ≠ authentication. SCIM gets the account there before first login; SAML/OIDC proves it at login. Know: PATCH vs PUT, filtering, bulk, and error handling / reconciliation.

JIT & account linking

JIT provisioning: create the local account on first federated login from assertion claims — no SCIM pre-provision needed.

Social + linking: match on verified email only, prompt to link, never auto-merge on unverified claims — that’s an account-takeover path.

Custom IdP as a factor, email magic link, and IdP chaining all sit here: the IdP delegates proof, the SP still owns the session and policy.

Token security — 2026 additions

DPoP & sender-constraining

Bearer tokens can be replayed by anyone who steals them. DPoP binds the token to a client key — each request carries a proof signature. mTLS does the same at transport layer. This is the direction for high-value APIs.

Refresh token rotation

Rotate on every use, detect reuse of an old token = theft signal → revoke the whole family. Short access-token lifetimes (5–15 min for sensitive APIs), refresh tokens only where a secure store exists.

PAR + RAR

PAR (Pushed Authorization Requests): send auth params back-channel, get a reference — nothing sensitive in the browser URL. RAR: rich, structured authorization details instead of flat scope strings.

Revocation reality

Stateless JWTs can’t be instantly revoked — mitigate with short expiry, token introspection for high-risk calls, and event-driven signals (Continuous Access Evaluation / Shared Signals) to kill sessions mid-flight.

Non-human & AI-agent identity

What hiring managers probe now

Every agent, workload, and service is an identity — and there are far more of them than humans. Principles that transfer directly from workforce IAM:

  • No long-lived secrets: workload identity federation / SPIFFE SVIDs — short-lived, attested credentials instead of static API keys in code.
  • Delegation, not impersonation: an agent acting for a user should carry a token that says both — who the user is and which agent is acting (act claim / token exchange, RFC 8693). Audit must separate the two.
  • Least privilege per task: scoped, short-lived, down-scoped tokens per tool call — not the user’s full session handed to the agent.
  • Human in the loop for high impact: step-up / approval when an agent’s action crosses a risk threshold, same pattern as contextual access for humans.
